# Шаблоны C++ без скачков

Пошаговый конспект для преподавателя. От обычной функции до concepts. Предполагается, что вы знаете переменные, классы, функции и обычные ссылки; сложные шаблоны изучаем с нуля.

## Как работать с конспектом

Это не справочник по синтаксису. Мы будем постоянно задавать один вопрос: **что именно мы не можем выразить уже знакомым способом?** Затем будем менять минимальный кусок программы и смотреть, что это даёт.

Главы 1–5 — подготовка к первому семинару. Главы 6–10 — подготовка ко второму. Не нужно запоминать все формы записи: важно уметь восстановить их из задачи.

Блоки с `main` — самостоятельные программы. Каждая сохранена в отдельном файле в `theory/examples/`; рядом с блоком есть ссылка на файл и команда запуска из корня репозитория. Остальные блоки — промежуточные фрагменты, не самостоятельные программы. Можно собрать все примеры командой `cmake --build build --target theory` или запустить их по очереди через `cmake --build build --target run-theory`. Перед первым запуском из корня проекта выполните `cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug`. Все примеры, кроме 23 и 24 (concepts, C++20), собираются как C++17. В основном проекте те же идеи применяются к рейтингу: [README проекта](../README.md).

```bash
clang++ -std=c++20 -Wall -Wextra \
    -Wpedantic main.cpp -o demo
./demo
```

На Linux можно заменить `clang++` на `g++`. Встроенные в C++ слова и названия библиотечных сущностей будут вводиться при первом использовании.

## 1. От обычной функции к функтору

### 1.1. Одна сортировка, разные правила

Представим список цен: 300, 100, 200. Иногда хотим показать дешёвые товары первыми, иногда дорогие. Алгоритм сортировки при этом один и тот же. Отличается только ответ на вопрос: должен ли элемент `a` стоять раньше элемента `b`?

Начнём с самой обычной функции.

Запускаемый пример: [`01_ordinary_sort.cpp`](examples/01_ordinary_sort.cpp).

```bash
cmake --build build --target run-theory-01_ordinary_sort
```

```cpp
#include <algorithm>
#include <iostream>
#include <vector>

bool cheaper(int a, int b) {
    // true: a должен стоять раньше b.
    return a < b;
}

int main() {
    std::vector<int> prices{300, 100, 200};

    // Передаём правило, а не результат его вызова.
    std::sort(prices.begin(), prices.end(),
              cheaper);

    for (int price : prices) {
        std::cout << price << ' ';
    }
}
```

Результат: `100 200 300`.

`std::sort` принимает начало, конец диапазона и компаратор. Выражение `cheaper` здесь не вызывает функцию: нет скобок с аргументами. Имя функции преобразуется в указатель на неё. Сортировка сама выбирает, какие пары элементов сравнивать, и вызывает переданное правило.

Упрощённо внутри алгоритма могло бы быть `if (compare(a, b)) ...`. Реальный `std::sort` гораздо сложнее; нас интересует только интерфейс компаратора.

Почему возвращаем `bool`? Сортировке нужен ответ «раньше или нет». Почему строго `<`, а не `<=`? Элемент не должен предшествовать самому себе. Компаратор обязан задавать строгое слабое упорядочение: в частности, нельзя считать одновременно `a` раньше `b` и `b` раньше `a`. Компилятор не проверяет эти математические свойства.

Для обратного порядка достаточно второй функции `more_expensive`, которая возвращает `a > b`. Ничего сложнее здесь пока не нужно.

### 1.2. Когда двух функций становится мало

Допустим, направление и критерий сортировки теперь являются настройками пользователя. У двух независимых списков могут быть разные настройки. Мы хотим передавать правило вместе с его настройкой, не используя глобальные переменные.

Попытка сделать функцию с третьим аргументом логична:

```cpp
bool compare_price(int a, int b,
                   bool ascending) {
    return ascending ? a < b : a > b;
}
```

`ascending` — направление, `?:` — условный оператор. Если направление истинно, вычисляется `a < b`; иначе `a > b`.

Но передать `compare_price` напрямую в `std::sort` нельзя: алгоритм вызывает компаратор с двумя аргументами, а наша функция требует три. У алгоритма нет параметра `ascending` и не должно быть: он не знает ничего о ценах.

Можно выбрать между двумя обычными функциями, и при единственной булевой настройке это вполне разумно. Но с произвольным набором настроек удобнее создать объект, который хранит их и умеет сравнивать элементы. Как заставить объект выглядеть как функция для вызывающего кода?

### 1.3. operator() — вызов объекта

Оператор `()` можно перегрузить для класса. Рассмотрим сначала его без сортировки:

Запускаемый пример: [`02_functor.cpp`](examples/02_functor.cpp).

```bash
cmake --build build --target run-theory-02_functor
```

```cpp
#include <iostream>

struct PriceOrder {
    bool ascending;

    bool operator()(int a, int b) const {
        return ascending ? a < b : a > b;
    }
};

int main() {
    PriceOrder cheap_first{true};
    PriceOrder expensive_first{false};

    std::cout << cheap_first(100, 300)
              << '\n';
    std::cout << expensive_first(100, 300)
              << '\n';
}
```

Результат: `1`, затем `0`.

Разбираем запись по частям:

`struct PriceOrder` — обычный пользовательский тип. Его член `bool ascending` хранит настройку конкретного объекта. `PriceOrder cheap_first{true}` создаёт объект и инициализирует этот член значением `true`. Фигурные скобки здесь — агрегатная инициализация, а не вызов оператора `()`.

`bool operator()(int a, int b)` — нестатическая функция-член. Её имя `operator()` сообщает компилятору, какую операцию мы перегружаем. Вторые скобки содержат список параметров этой функции. Слева `bool` — тип результата сравнения.

`const` после списка параметров означает, что метод не изменяет обычные поля объекта. Это логично: сравнивая два элемента, мы читаем настройку, но не меняем направление сортировки. Кроме того, такой метод можно вызвать для константного экземпляра `PriceOrder`.

`cheap_first(100, 300)` — сокращённая запись `cheap_first.operator()(100, 300)`. Оба вызова используют один и тот же объект с его полем `ascending`.

Теперь можем передавать `PriceOrder{true}` или `PriceOrder{false}` в `std::sort`: для сортировки оба объекта поддерживают ровно нужный вызов с двумя числами.

```cpp
// Продолжение: PriceOrder уже определён.
std::sort(prices.begin(), prices.end(),
          PriceOrder{true});
```

Объект, который можно вызвать через `()`, называют функтором (function object). Это не особый вид переменной, а обычный объект класса с подходящим оператором вызова.

**Выигрыш:** состояние и поведение собраны вместе; два объекта независимы; не нужны глобальные переменные. Шаблонный алгоритм получает конкретный тип функтора и может оптимизировать его вызов, хотя встраивание не гарантируется.

**Цена:** нужно объявлять отдельный тип. Для одного простого сравнения это лишний код. Для многократно используемого, сложного или именованного правила — нормальное решение.

## 2. bind и лямбды: как получить вызываемый объект

### 2.1. Что адаптирует std::bind

Вернёмся к трёхпараметрической `compare_price`. Допустим, она уже есть в библиотеке, изменять её мы не хотим. Нужно создать правило для `sort`, заранее зафиксировав направление и оставив два аргумента свободными.

Запускаемый пример: [`03_bind.cpp`](examples/03_bind.cpp).

```bash
cmake --build build --target run-theory-03_bind
```

```cpp
#include <functional>
#include <iostream>

bool compare_price(int a, int b,
                   bool ascending) {
    return ascending ? a < b : a > b;
}

int main() {
    using namespace std::placeholders;

    auto rule = std::bind(compare_price,
                          _1, _2, true);

    std::cout << rule(100, 300) << '\n';
}
```

Результат: `1`.

`<functional>` — заголовок, где объявлены `std::bind` и плейсхолдеры. `using namespace std::placeholders` позволяет писать `_1` вместо `std::placeholders::_1`; лучше ограничивать такой using небольшой областью, как здесь.

`std::bind(compare_price, _1, _2, true)` не выполняет сравнение сейчас. Он создаёт объект, который хранит вызываемую функцию и связанные аргументы. При будущем вызове объекта `_1` означает первый переданный аргумент, `_2` — второй; `true` уже сохранён.

Раскроем вызов вручную:

- `rule(100, 300)` даёт первый аргумент 100 и второй 300.
- `_1` заменяется на 100, `_2` на 300.
- сохранённое направление равно `true`.
- вызывается `compare_price(100, 300, true)`.

Почему `auto`? У результата `bind` есть реальный тип, но стандарт не даёт удобного имени этого типа. Нам не нужно его знать: компилятор выводит тип переменной из инициализатора. Это не динамическая типизация.

По умолчанию `bind` хранит обычные связанные аргументы в виде значений с преобразованием decay (в частности, ссылки убираются). `std::ref(x)` позволяет явно связать ссылку на существующий объект; тогда нужно следить за временем его жизни. Плейсхолдеры обрабатываются специально.

Исторически `bind` удобен для частичного связывания аргументов и их перестановки. Например, `_2, _1, true` меняет местами входные параметры. В старых библиотеках и коде C++11 его можно встретить часто.

### 2.2. Та же задача лямбдой

Зачем вводить ещё одну конструкцию? В `bind` мы сначала читаем функцию, затем плейсхолдеры и мысленно подставляем параметры. При сложном правиле это становится неудобно. Лямбда позволяет прямо написать, что происходит при вызове.

Запускаемый пример: [`04_lambda.cpp`](examples/04_lambda.cpp).

```bash
cmake --build build --target run-theory-04_lambda
```

```cpp
#include <iostream>

bool compare_price(int a, int b,
                   bool ascending) {
    return ascending ? a < b : a > b;
}

int main() {
    bool ascending = true;

    auto rule = [ascending](int a, int b) {
        return compare_price(a, b, ascending);
    };

    ascending = false;

    // Внутри rule сохранена копия true.
    std::cout << rule(100, 300) << '\n';
}
```

Результат снова `1`. Изменение внешней переменной не меняет сохранённую копию.

Разберём форму `[ascending](int a, int b) { ... }` слева направо.

Квадратные скобки — список захватов: что объект должен получить из окружающего контекста при создании. `[ascending]` захватывает значение. Пустые `[]` означают, что захвата локальных переменных нет.

Круглые скобки — параметры будущего вызова, здесь два числа. Фигурные скобки — тело будущего вызова. В данном случае тип результата выводится как `bool` из `return`; при желании можно написать `-> bool` после параметров.

Точка с запятой после `}` нужна потому, что заканчивается объявление переменной `rule` с инициализатором-лямбдой.

В мысленной модели компилятор создаёт безымянный класс с сохранённым `ascending` и оператором вызова. Это не точное описание всех правил реализации, но позволяет понять, почему результат лямбды можно передать в `sort` так же, как функтор.

По умолчанию оператор вызова лямбды константный. `mutable` разрешает изменять захваченные копии. Захват `[&ascending]` вместо `[ascending]` позволяет обращаться к исходной переменной, но объект не должен использоваться после окончания её жизни.

**Выбор в обычном коде:** короткое локальное правило — лямбда. Сложное многократно используемое правило с понятным именем — класс-функтор. Адаптация существующего вызова через `bind` возможна, но обычно лямбда яснее. Лямбды не отменили функторы: сами создают function objects. Они не гарантируют более высокую скорость, чем `bind`.

## 3. Ссылки: что нужно знать до forwarding

### 3.1. Объект, тип, выражение — три разных понятия

Этот раздел принципиален. Прежде чем писать `T&&`, разберём, зачем нужны два вида ссылок.

```cpp
int a = 10;
int& r = a;
```

`a` — имя объекта типа `int`, в памяти есть значение 10. `r` — ссылка, то есть другое имя для того же объекта. `r = 20` меняет `a`, а не отдельную копию. Ссылка в языке не является самостоятельным объектом; реализация может использовать память для её представления, но это не смысл ссылки.

Выражение — фрагмент программы, который вычисляет значение, обозначает объект или выполняет операцию. `a`, `r`, `a + 1`, `42`, вызов функции — выражения. Категория выражения описывает свойства результата выражения, а не просто тип переменной.

`a` как выражение — lvalue: оно обозначает объект с идентичностью. Можно получить его адрес, читать его повторно. Но возможность изменить объект не является обязательным свойством lvalue: `const int c = 5;` тоже даёт lvalue при выражении `c`.

`42` и `a + 1` — prvalue: вычисляют значение. Они не обозначают заранее существующий объект `a`. Когда такое значение нужно связать со ссылкой, может материализоваться временный объект.

Есть ещё xvalue — выражение, которое обозначает существующий объект, но допускает обращение к нему как к ресурсу, пригодному для перемещения. Например `std::move(a)`. Оно не уничтожает `a` и не перемещает его само.

Для наших задач достаточно помнить: lvalue — один вид выражений; rvalue объединяет prvalue и xvalue. У prvalue и xvalue разные формальные свойства, поэтому не стоит определять rvalue как «любой временный объект».

### 3.2. Зачем перегружать функции по ссылкам

Представим очередь отправки сообщений. Если передано существующее сообщение, которое пользователь продолжит использовать, хотим его скопировать в очередь. Если передан временный объект или пользователь явно разрешил забрать ресурс, можем переместить строку в очередь.

Запускаемый пример: [`05_reference_overloads.cpp`](examples/05_reference_overloads.cpp).

```bash
cmake --build build --target run-theory-05_reference_overloads
```

```cpp
#include <iostream>
#include <string>
#include <utility>
#include <vector>

std::vector<std::string> queue;

void enqueue(const std::string& text) {
    // Копируем: источник остаётся прежним.
    queue.push_back(text);
    std::cout << "copy\n";
}

void enqueue(std::string&& text) {
    // text по имени — lvalue.
    // Явно разрешаем move для push_back.
    queue.push_back(std::move(text));
    std::cout << "move\n";
}

int main() {
    std::string message = "Hello";
    enqueue(message);
    enqueue(std::string{"Temporary"});
    enqueue(std::move(message));
}
```

Результат: `copy`, `move`, `move`. Это метки выбранных перегрузок; они не доказывают конкретное число аллокаций или отсутствие копирования внутри реализации строки.

Первая перегрузка `const std::string&` привязывается к существующей строке без копирования на входе, разрешает её прочитать. Она также может привязаться к rvalue, но когда есть вторая подходящая перегрузка с неконстантной rvalue-ссылкой, она будет предпочтительна для неконстантного rvalue.

Вторая `std::string&&` — rvalue-ссылка на конкретный тип. Она принимает временную строку или `std::move(message)`, но не обычное выражение `message`.

Почему внутри второй функции снова нужен `std::move`? Потому что выражение `text` обозначает объект по имени. Независимо от объявленного типа ссылки, выражение с именем такой переменной — lvalue. Если вызвать `push_back(text)`, будет выбран вариант копирования.

`std::move(text)` из `<utility>` преобразует выражение в rvalue (обычно xvalue). Перемещение выполняет уже подходящий конструктор или оператор присваивания, вызванный вследствие этого преобразования. Если такого подходящего move нет, может быть вызвана копирующая операция. Для `std::string` перемещённый объект остаётся валидным, но его содержимое не следует считать заранее известным.

Почему нельзя всегда использовать move? Потому что пользователь может ожидать, что существующее сообщение сохранит прежнее значение. Мы изменили бы семантику функции.

### 3.3. Что выводит шаблон по аргументу

До forwarding вспомним обычный шаблон:

```cpp
template<class T>
void by_value(T x) {
    // Здесь x — локальный объект.
}
```

При `by_value(10)` компилятор выводит `T = int`. При `int a = 10; by_value(a);` тоже `T = int`. Передача по значению не запоминает, был ли исходный аргумент lvalue; для обычных объектов верхнеуровневый const также не сохраняется. Ссылки при таком выводе не становятся частью `T`.

Заменим параметр на `T&`:

```cpp
template<class T>
void by_ref(T& x) {
    // x — ссылка на исходный объект.
}
```

`by_ref(a)` даёт `T = int`, параметр `int&`. Если `const int c = 10`, то `by_ref(c)` даёт `T = const int`, параметр `const int&`. Временное `by_ref(10)` не подходит: обычная неконстантная lvalue-ссылка не привязывается к такому значению.

`const T&` позволяет читать и lvalue, и rvalue, но при дальнейшей передаче `x` будет константным lvalue. Для функции, которая только читает объект, этого достаточно. Для обёртки над двумя перегрузками `enqueue` — нет.

## 4. Forwarding reference: не потерять намерение вызывающего

### 4.1. Конкретная поломка

Хотим добавить логирование перед отправкой сообщения. Логирование не должно менять то, какую перегрузку `enqueue` выберет компилятор.

Наивная обёртка:

```cpp
// enqueue — две перегрузки из главы 3.
void log_enqueue(const std::string& text) {
    std::cout << "sending\n";
    enqueue(text);
}
```

Даже если пользователь передаст временную строку, `text` внутри — константное lvalue, поэтому будет выбрано копирование. Написать две перегрузки `log_enqueue` можно, и для одного конкретного типа это хорошее решение. Но универсальная обёртка для многих типов и категорий аргументов потребует много таких перегрузок.

Нам нужен способ принять аргумент, сохранить сведения о его типе и категории и затем передать его дальше.

### 4.2. Почему именно T&&

```cpp
template<class T>
void relay(T&& x) {
    // Здесь позже появится передача дальше.
}
```

Особенность `T&&` здесь не в том, что это «ссылка, которая всегда принимает всё». Особенность в правилах вывода: если параметр является rvalue-ссылкой на неквалифицированный выводимый параметр типа шаблона, для lvalue компилятор выводит `T` как lvalue-ссылку. Такой параметр называется forwarding reference (исторически universal reference).

Пусть `int a = 5; const int c = 7;`.

При `relay(a)` аргумент — lvalue типа `int`. Специальное правило вывода даёт `T = int&`. Подставляем это в `T&&`: получается комбинация `int& &&`. Правило схлопывания превращает её в `int&`.

При `relay(c)` аналогично `T = const int&`, итоговый параметр `const int&`.

При `relay(42)` аргумент — rvalue типа `int`. Выводится `T = int`, параметр `int&&`.

При `relay(std::move(a))` тоже `T = int`, параметр `int&&`.

### 4.3. Reference collapsing — зачем оно существует

В исходном коде нельзя просто объявить `int& & r`. Но при подстановке параметров шаблона и использовании псевдонимов типов могут возникать комбинации ссылок. Язык определяет, какой один тип ссылки получается.

| Комбинация | Результат |
|---|---|
| `&` + `&` | `&` |
| `&` + `&&` | `&` |
| `&&` + `&` | `&` |
| `&&` + `&&` | `&&` |

Правило для запоминания: если хотя бы одна ссылка lvalue, результат lvalue-ссылка. Только две rvalue-ссылки дают rvalue-ссылку.

Без схлопывания подстановка `T = int&` в `T&&` давала бы недопустимый тип. Вместе с особым правилом вывода эта конструкция позволяет одному шаблону работать с обеими категориями.

Проверим не на догадках, а на компиляторе.

Запускаемый пример: [`06_reference_collapsing.cpp`](examples/06_reference_collapsing.cpp).

```bash
cmake --build build --target run-theory-06_reference_collapsing
```

```cpp
#include <type_traits>
#include <utility>

template<class T>
void inspect(T&& x) {
    // decltype(x) — объявленный тип x.
    static_assert(
        std::is_same_v<decltype(x), T&&>);

    // (x) — выражение, и оно lvalue.
    static_assert(
        std::is_lvalue_reference_v<
            decltype((x))>);
}

int main() {
    int a = 5;
    const int c = 7;
    inspect(a);
    inspect(c);
    inspect(42);
    inspect(std::move(a));
}
```

Программа ничего не выводит: успешная компиляция — результат эксперимента.

`<type_traits>` содержит инструменты проверки типов. `std::is_same_v<A, B>` равно `true`, если типы совпадают; `std::is_lvalue_reference_v<A>` проверяет, является ли `A` lvalue-ссылкой. `static_assert` требует истинного условия при компиляции. С ним мы проверяем выводы, не исполняя программу.

Почему две формы `decltype`? Для непомещённого в скобки имени переменной `decltype(x)` даёт объявленный тип. Для общего выражения `decltype((x))` результат зависит от категории: для lvalue типа `U` это `U&`. Дополнительные скобки не изменили категорию, а изменили то, какое правило `decltype` применяется.

### 4.4. T&& принимает, forward передаёт

Теперь вернёмся к задаче логирования. Даже если компилятор сохранил сведения в `T`, выражение `x` по имени остаётся lvalue. Значит, простой вызов `receive(x)` потеряет исходную категорию.

Запускаемый пример: [`07_forwarding.cpp`](examples/07_forwarding.cpp).

```bash
cmake --build build --target run-theory-07_forwarding
```

```cpp
#include <iostream>
#include <string>
#include <utility>

void receive(const std::string&) {
    std::cout << "read/copy\n";
}

void receive(std::string&&) {
    std::cout << "can move\n";
}

template<class T>
void bad_relay(T&& x) {
    // Ошибка: x всегда lvalue-выражение.
    receive(x);
}

template<class T>
void relay(T&& x) {
    // Восстанавливаем категорию по T.
    receive(std::forward<T>(x));
}

int main() {
    std::string s = "hello";
    bad_relay(std::string{"temp"});
    relay(s);
    relay(std::string{"temp"});
}
```

Вывод:

```text
read/copy
read/copy
can move
```

Имена параметров у `receive` не нужны: эти функции показывают только выбор перегрузки, а не выполняют перемещение. В реальной `enqueue` ресурс перемещался бы в контейнер.

Почему `std::forward<T>` требует указать `T`? Нужен именно тип, который был выведен на входе обёртки. Если выводить тип заново только из выражения `x`, увидим lvalue и потеряем информацию о том, как пришёл аргумент.

Для понимания используем модель первого варианта библиотечной функции:

```cpp
// Учебная модель, не полная реализация.
template<class T>
T&& my_forward(
    std::remove_reference_t<T>& x) noexcept {
    return static_cast<T&&>(x);
}
```

`remove_reference_t<T>` удаляет ссылку из типа. Например, из `std::string&` получается `std::string`. Добавляем `&`, чтобы параметр `my_forward` принимал lvalue `x` из обёртки. `noexcept` сообщает, что эта операция не бросает исключений.

`static_cast<T&&>(x)` выполняет нужное преобразование. При `T = std::string&` целевой тип после схлопывания — `std::string&`, результат lvalue. При `T = std::string` целевой тип — `std::string&&`, результат xvalue. Это механизм, а не магия. Стандартный `std::forward` имеет и другую перегрузку для rvalue-аргумента и дополнительные требования; приведённой модели достаточно для именованного параметра обёртки.

Почему не `std::move(x)`? Он преобразовал бы в rvalue даже исходное lvalue `s`. `forward` сохраняет намерение вызывающего, `move` явно разрешает использовать объект как источник перемещения. Ни один из них сам не копирует и не перемещает данные.

### 4.5. Где применять, где не применять

Типичный пример — фабрика объектов, которая передаёт аргументы конструктора, или `emplace_back` контейнера. Обёртка с одним параметром `T&&` и `forward<T>` позволяет не дублировать все варианты перегрузок.

Если функция только читает объект, обычно достаточно `const T&`. Если ей нужна собственная копия, `T value` и последующий `std::move(value)` часто проще. Если она всегда забирает ресурс известного типа, `std::string&&` прямо выражает это намерение.

Не каждое `&&` — forwarding reference. `const T&&` не подходит под специальное правило. `std::vector<T>&&` — тоже нет, потому что параметр не является непосредственно `T&&`. В `template<class T> struct Box { void set(T&&); };` тип `T` уже определяется при выборе `Box<T>`, а не выводится из аргумента `set`, поэтому это обычная rvalue-ссылка.

Forwarding не продлевает время жизни временного объекта. Не сохраняйте ссылку на такой аргумент для позднего использования без гарантии времени жизни. И не следует автоматически делать forward одного потенциально перемещаемого объекта несколько раз: первый потребитель может забрать его ресурс.

## 5. Variadic templates: от двух аргументов к произвольному числу

### 5.1. Проблема, которую не решает обычный шаблон

Пусть нужно выводить строки отчёта: иногда имя и балл, иногда место, имя и балл, иногда только итог. Обычная функция с двумя параметрами позволяет передавать разные значения, но количество аргументов фиксировано.

```cpp
template<class A, class B>
void print_two(const A& a, const B& b) {
    std::cout << a << ' ' << b << '\n';
}
```

`A` и `B` могут быть разными типами. Вызов `print_two("Anna", 95)` корректен, но `print_two(1, "Anna", 95)` — нет: функция требует ровно два аргумента. Можно написать ещё одну перегрузку, но с каждым форматом мы будем дублировать вывод.

Контейнер `vector<string>` решает задачу переменного количества строк во время выполнения, но требует заранее преобразовать числа в строки. Если количество и типы аргументов известны при компиляции, можно обойтись без промежуточного контейнера.

### 5.2. Как читать три точки

Запускаемый пример: [`08_pack_size.cpp`](examples/08_pack_size.cpp).

```bash
cmake --build build --target run-theory-08_pack_size
```

```cpp
#include <iostream>

template<class... Ts>
void count(const Ts&... xs) {
    // Число параметров функции.
    std::cout << sizeof...(xs) << '\n';
}

int main() {
    count(1, 2.5, "Anna");
    count(42);
    count();
}
```

Вывод: 3, 1, 0.

`class... Ts` объявляет пакет шаблонных параметров-типов. `Ts` — не один тип и не контейнер, а последовательность типов, длина которой известна при инстанцировании.

`const Ts&... xs` объявляет пакет параметров функции. Для каждого типа из `Ts` образуется отдельный параметр `const T&`. `xs` обозначает пакет этих параметров.

При первом вызове компилятор выводит пакет типов `int`, `double`, `char[5]` (строковый литерал "Anna" содержит ещё завершающий ноль). Из него формируется три параметра. При втором — один параметр, при третьем — ни одного.

`sizeof...(Ts)` — специальный оператор подсчёта элементов пакета, не размер в байтах. В программе используем `sizeof...(xs)`: это число параметров функции, совпадающее с числом типов.

Почему нельзя написать `std::cout << xs`? `xs` — целый пакет, а оператор `<<` ожидает один правый операнд. Нужно указать, как применить операцию ко всем элементам. Это называется раскрытием пакета.

### 5.3. Сначала решение без fold expressions

Представим, что у нас три значения. Можно обработать первое, затем вызвать ту же функцию для оставшихся двух, затем для одного, затем остановиться. Это обычная идея рекурсии, но разные длины пакетов дают разные специализации шаблона.

Запускаемый пример: [`09_recursive_print.cpp`](examples/09_recursive_print.cpp).

```bash
cmake --build build --target run-theory-09_recursive_print
```

```cpp
#include <iostream>

// Базовый случай: аргументов больше нет.
void print_all() {
    std::cout << '\n';
}

template<class First, class... Rest>
void print_all(const First& first,
               const Rest&... rest) {
    std::cout << first << ' ';

    // Раскрываем только оставшиеся аргументы.
    print_all(rest...);
}

int main() {
    print_all(1, "Anna", 95);
}
```

Вывод: `1 Anna 95` (с пробелом после последнего поля).

Почему `First` отдельно от `Rest`? Нам нужно выделить один аргумент, который можно обработать обычным выражением `std::cout << first`. `Rest` содержит все остальные типы. В `print_all(rest...)` три точки после имени раскрывают пакет в список отдельных аргументов.

Проследим вызовы:

- `print_all(1, "Anna", 95)` печатает 1 и вызывает `print_all("Anna", 95)`.
- Второй вызов печатает Anna, вызывает `print_all(95)`.
- Третий печатает 95, вызывает `print_all()`.
- Обычная функция без параметров печатает перевод строки и завершает цепочку.

Зачем базовый случай объявлен раньше шаблона? Чтобы он был виден при поиске имени `print_all` внутри шаблона. Так мы не полагаемся на дополнительные правила поиска имён.

Решение работает, но для такой простой операции приходится писать базовый случай, выделять первый параметр и повторять вызовы. С C++17 можно выразить последовательную обработку одной конструкцией.

### 5.4. Fold expression без магии

Запускаемый пример: [`10_comma_fold.cpp`](examples/10_comma_fold.cpp).

```bash
cmake --build build --target run-theory-10_comma_fold
```

```cpp
#include <iostream>

template<class... Ts>
void print_all(const Ts&... xs) {
    // Одна операция вывода для каждого xs.
    ((std::cout << xs << ' '), ...);
    std::cout << '\n';
}

int main() {
    print_all(1, "Anna", 95);
    print_all();
}
```

Вывод первой строки тот же, вторая строка пустая.

Разберём `((std::cout << xs << ' '), ...);` от внутренней части к внешней.

`(std::cout << xs << ' ')` — шаблон выражения для одного элемента пакета. В нём участвует `xs`, значит, выражение можно повторить для каждого аргумента.

`,` — оператор запятая. У встроенного оператора запятая левый операнд вычисляется раньше правого. Это позволяет выполнить несколько операций по порядку.

`(expression, ...)` — унарная правая свёртка по запятой. Внешние скобки обязательны: это часть синтаксиса fold expression, а не просто украшение. Для трёх аргументов получается выражение вида:

```cpp
// Мысленное раскрытие для конкретного вызова.
((std::cout << 1 << ' '),
 ((std::cout << "Anna" << ' '),
  (std::cout << 95 << ' ')));
```

Почему правая группировка не меняет порядок печати? Потому что встроенная запятая вычисляет левую часть до правой. Скобки определяют группировку, не обращают этот порядок.

Здесь операнды — стандартный поток, и используется встроенная запятая. В более общем коде с пользовательскими типами можно явно привести каждую операцию к `void`, чтобы исключить перегруженную запятую.

Пустой пакет допустим: унарная свёртка по запятой для него даёт `void()`, то есть никаких операций. Перевод строки находится после свёртки, поэтому выводится даже при нуле полей.

### 5.5. Fold не обязательно выводит: пример суммы

Запускаемый пример: [`11_sum_fold.cpp`](examples/11_sum_fold.cpp).

```bash
cmake --build build --target run-theory-11_sum_fold
```

```cpp
#include <iostream>

template<class... Ts>
auto sum(Ts... xs) {
    return (0 + ... + xs);
}

int main() {
    std::cout << sum(1, 2, 3) << '\n';
    std::cout << sum() << '\n';
}
```

Результат 6, затем 0. Начальное значение `0` делает сумму пустого пакета определённой. `(0 + ... + xs)` — бинарная левая свёртка: `((0 + 1) + 2) + 3`.

Для понимания достаточно двух изученных форм. Полная карта форм (P — выражение с пакетом, I — начальное значение, op — оператор):

| Форма | Группировка для a, b, c |
|---|---|
| `(P op ...)` | `a op (b op c)` |
| `(... op P)` | `(a op b) op c` |
| `(I op ... op P)` | `((I op a) op b) op c` |
| `(P op ... op I)` | `a op (b op (c op I))` |

Для неассоциативных операций группировка важна: `10 - (3 - 2)` даёт 9, а `(10 - 3) - 2` — 5. Не путайте группировку с порядком вычисления операндов: он зависит от оператора.

Унарные fold expressions допускают пустой пакет только для `&&` (результат true), `||` (false) и запятой (`void()`). Для других операторов нужен непустой пакет или начальное значение. Сумма с `0` не универсальна для всех типов: она требует подходящей операции `0 + первое_значение`.

### 5.6. Когда объединять пакеты с forwarding

В функции печати нам достаточно `const Ts&...`: мы только читаем поля. Не нужно писать forwarding ради самого forwarding. Но если наша задача — передать неизвестное число аргументов конструктору, необходимо сохранить категорию каждого аргумента.

Запускаемый пример: [`12_forwarding_factory.cpp`](examples/12_forwarding_factory.cpp).

```bash
cmake --build build --target run-theory-12_forwarding_factory
```

```cpp
#include <memory>
#include <string>
#include <utility>

template<class T, class... Args>
std::unique_ptr<T> make_object(Args&&... args) {
    // Каждый аргумент передаём с его типом.
    return std::make_unique<T>(
        std::forward<Args>(args)...);
}

int main() {
    auto s = make_object<std::string>(3, 'x');
    return *s == "xxx" ? 0 : 1;
}
```

`std::unique_ptr<T>` владеет созданным объектом и освобождает его автоматически. `std::make_unique<T>` создаёт такой объект, передавая аргументы конструктору `T`. Мы используем его как готовый безопасный механизм выделения памяти: цель примера — именно передача параметров.

`T` указываем явно: `make_object<std::string>` сообщает, что хотим создать строку. `Args` выводится из `3` и `'x'` как пакет `int, char`. `Args&&... args` формирует отдельную forwarding reference для каждого аргумента. При lvalue соответствующий элемент `Args` будет ссылкой.

`std::forward<Args>(args)...` раскрывает целый шаблон выражения. Для данного вызова это два отдельных аргумента: `std::forward<int>(args_0)` и `std::forward<char>(args_1)`. Точки стоят после скобок вызова, потому что повторяется всё выражение, а не только имя `args`.

Преимущество variadic templates — один интерфейс для множества сигнатур. Недостатки — более сложные ошибки, дополнительные инстанцирования и потенциальный рост времени компиляции и размера кода. Это не замена контейнеру для количества элементов, известного только во время выполнения.

## 6. Зачем вообще ограничивать шаблоны

### 6.1. Вводим новую задачу

До этого мы учились принимать произвольные аргументы. Теперь нужно выяснить, какие из них подходят для конкретной операции. Представим функцию отчёта `write_max`: принимает два значения одного типа и пишет большее в поток.

Запускаемый пример: [`13_unconstrained_max.cpp`](examples/13_unconstrained_max.cpp).

```bash
cmake --build build --target run-theory-13_unconstrained_max
```

```cpp
#include <iostream>
#include <string>

template<class T>
void write_max(std::ostream& out,
               const T& a, const T& b) {
    // Выбираем большее, затем выводим.
    out << (a < b ? b : a) << '\n';
}

int main() {
    write_max(std::cout, 3, 7);
    write_max(std::cout, std::string{"A"},
                        std::string{"B"});
}
```

Результат: 7 и B. Строки сравниваются лексикографически.

Почему `const T&`? Ничего не копируем и не изменяем; требуется сравнить и прочитать значения. Почему `std::ostream& out`, а не всегда `std::cout`? Тогда можно выводить в любой подходящий поток, например файл. Сам поток изменяет внутреннее состояние при выводе, поэтому ссылка неконстантная.

Скобки вокруг `a < b ? b : a` нужны, чтобы сначала выбрать значение, а затем применить `<<`: у операторов разные приоритеты.

Какие требования к `T` фактически есть? Выражение `a < b` должно быть допустимым, его результат должен подходить для условия, и выбранное значение должно поддерживать потоковый вывод. Для предсказуемого интерфейса далее будем требовать, чтобы результат `out << value` имел тип `std::ostream&`. Это договорённость, соответствующая обычным перегрузкам потокового вывода. Она позволяет продолжать цепочку `<< '\n'`.

### 6.2. Проверяем пользовательские типы

```cpp
struct Note {
    int id;
};

struct Score {
    int points;
};

bool operator<(const Score& a,
               const Score& b) {
    return a.points < b.points;
}

std::ostream& operator<<(
    std::ostream& out, const Score& s) {
    return out << s.points;
}
```

Здесь `Note` — обычная структура без операторов. Наличие поля `id` не создаёт автоматически `<` и `<<`. `Score` явно поддерживает обе операции. У `operator<<` первым параметром служит поток, вторым — объект; возвращаем тот же поток по ссылке, чтобы разрешить цепочки вывода.

Вызов `write_max(std::cout, Score{3}, Score{7})` работает. Вызов с двумя `Note` приводит к ошибке. Но почему это проблема? Ведь компилятор и так не позволит выполнить неправильный код.

### 6.3. Три стадии, которые нужно различать

Упрощённая модель компиляции вызова шаблонной функции:

1. Компилятор находит объявления с нужным именем, выводит и подставляет шаблонные аргументы в объявления. Учитываются ограничения и допустимость кандидатов.
2. Из подходящих кандидатов выбирается лучшая перегрузка по правилам разрешения перегрузок.
3. Если для выбранной специализации нужна реализация, инстанцируется тело. Некорректный код в теле даёт ошибку.

Это учебная схема, а не полный алгоритм стандарта: в частности, некоторые свойства декларации могут требовать дополнительного инстанцирования. Для наших функций с явным возвращаемым типом `void` она объясняет главное.

У обычного `write_max` объявление подходит и для `Note`: `const Note&` — вполне допустимый параметр. Проблема обнаруживается только в теле. Компилятор уже выбрал функцию; он не возвращается к выбору другой перегрузки только потому, что тело оказалось некорректным.

Для простого закрытого приложения этого может быть достаточно. Но библиотечному интерфейсу полезно уметь сказать заранее: «этот кандидат не предназначен для такого типа». Тогда возможно, например, выбрать другую перегрузку.

### 6.4. Почему static_assert и if constexpr — не то же самое

`static_assert` внутри функции проверяет условие при инстанцировании тела. Он хорош для понятного сообщения о нарушении внутреннего предположения. Но не исключает функцию из списка кандидатов.

`if constexpr` выбирает подходящую ветку внутри уже выбранной шаблонной функции. Например, при наличии сравнения выполняем сравнение, иначе выводим предупреждение. Это хорошо, если все типы должны приниматься, но обрабатываться по-разному.

Если же хотим, чтобы функция вообще не была подходящим кандидатом для `Note`, нужно выразить требование в объявлении шаблона. В C++17 для этого используют SFINAE, в C++20 — constraints/concepts. Прежде чем писать длинный `enable_if`, нужно научиться задавать компилятору простой вопрос: допустимо ли выражение `a < b` для типа `T`?

## 7. Учимся проверять выражения: decltype и declval

### 7.1. Что возвращает decltype

`decltype` — оператор языка, результат которого является типом, а не значением. Он позволяет узнать тип выражения без его выполнения.

Запускаемый пример: [`14_decltype.cpp`](examples/14_decltype.cpp).

```bash
cmake --build build --target run-theory-14_decltype
```

```cpp
#include <type_traits>

int main() {
    int x = 5;
    using A = decltype(x);
    using B = decltype(x + 1);
    using C = decltype(x < 10);

    static_assert(std::is_same_v<A, int>);
    static_assert(std::is_same_v<B, int>);
    static_assert(std::is_same_v<C, bool>);
}
```

`using A = ...` объявляет псевдоним типа. Это не создание объекта. `decltype(x < 10)` даёт `bool`, поскольку встроенное сравнение возвращает `bool`.

Важно: `decltype` не вычисляет результат сравнения. Оно проверяет, что выражение корректно, и определяет его тип. Это unevaluated operand — невычисляемый операнд.

Можно написать `decltype(1 / 0)` и получить `int`: деление не выполняется. Но `decltype(1 + std::string{"text"})` будет ошибкой: такой операции сложения нет. Невычисляемый контекст не отменяет проверку корректности выражения. И наоборот, проверка корректности типов не доказывает безопасность операции при выполнении.

### 7.2. Как проверить неизвестный тип без настоящего объекта

Допустим, хотим определить тип `a < b`, не имея реальных `a` и `b`. Первая мысль:

```cpp
// Проблема: требует T{}.
template<class T>
using less_result = decltype(T{} < T{});
```

`T{}` означает создание значения данного типа. Даже если оно не будет создано во время выполнения, выражение должно быть допустимым. Тип без подходящего конструктора по умолчанию не пройдёт такую проверку, хотя сравнивать уже существующие объекты может быть можно.

Ещё один недостаток: `T{}` — prvalue, а наша `write_max` сравнивает константные lvalue. Нужно проверять именно ту форму аргумента, которую использует реальная функция.

`std::declval<T>()` из `<utility>` позволяет получить выражение подходящего типа в невычисляемом контексте. Объект не создаётся.

Запускаемый пример: [`15_declval.cpp`](examples/15_declval.cpp).

```bash
cmake --build build --target run-theory-15_declval
```

```cpp
#include <type_traits>
#include <utility>

struct Score {
    explicit Score(int n) : points(n) {}
    int points;
};

bool operator<(const Score& a,
               const Score& b) {
    return a.points < b.points;
}

template<class T>
using less_result = decltype(
    std::declval<const T&>() <
    std::declval<const T&>());

int main() {
    static_assert(std::is_same_v<
        less_result<Score>, bool>);
}
```

`Score` имеет конструктор с обязательным аргументом. `Score{}` недопустимо. Но программа успешно компилируется: проверка не требует создания объекта.

Разберём внутреннюю запись:

`const T&` — хотим смоделировать константное lvalue. При `T = Score` это `const Score&`.

`std::declval<const T&>()` — вызов, который можно использовать в `decltype`. Объявленный возвращаемый тип `declval<U>` основан на `std::add_rvalue_reference_t<U>`. Для `U = const Score&` схлопывание ссылок оставляет `const Score&`. Поэтому результат выражения — lvalue. Для `declval<Score>()` результатом был бы rvalue, что не обязательно соответствует задаче.

Внешний `<` связывает два таких выражения. `decltype` получает тип результата сравнения, здесь `bool`. Всё проверяется при компиляции, ничего не сравнивается при выполнении.

`declval` нельзя использовать для получения реального объекта: его вызов в вычисляемом контексте недопустим. Это инструмент проверки типов, не фабрика и не функция, возвращающая «пустой объект».

### 7.3. Проверяем ровно требуемую операцию

Недостаточно лишь проверить наличие `<`. Например, оператор может возвращать пользовательский объект, который нельзя использовать как условие. Поэтому будем проверять преобразование результата к `bool`.

```cpp
template<class T>
using compare_result = decltype(
    static_cast<bool>(
        std::declval<const T&>() <
        std::declval<const T&>()));
```

Почему `static_cast<bool>`? Это та операция, которую хотим разрешить в нашем интерфейсе. Для обычного `bool` она ничего не меняет, но позволяет проверить преобразование результата пользовательского сравнения. В дальнейшем реализация `write_max` тоже будет явно использовать `static_cast<bool>`, чтобы проверка совпадала с кодом. Это конкретный договор, а не универсальное определение «сравнимого типа».

Для печати нужно моделировать и поток:

```cpp
template<class T>
using output_result = decltype(
    std::declval<std::ostream&>() <<
    std::declval<const T&>());
```

Здесь `std::ostream&` — изменяемый lvalue-поток, а `const T&` — читаемый объект. Проверяем оператор в том же направлении, что и в реальном коде. Не наоборот.

Если `T` не поддерживает операцию, пока что такой псевдоним при прямом использовании приводит к ошибке. `decltype` и `declval` сами не превращают ошибку в `false`. Для этого понадобится контекст, в котором компилятор может отбросить неподходящий шаблон.

## 8. Expression SFINAE: как неудачная подстановка исключает кандидата

### 8.1. Сначала без void_t и enable_if

Возьмём очень простую задачу: если тип можно сравнивать, сравнить два значения; иначе сообщить, что сравнение недоступно. Нам нужны две перегрузки, а не только сообщение об ошибке.

Запускаемый пример: [`16_expression_sfinae.cpp`](examples/16_expression_sfinae.cpp).

```bash
cmake --build build --target run-theory-16_expression_sfinae
```

```cpp
#include <iostream>

struct Note {};

// Основная перегрузка: сравнение доступно.
template<class T>
auto inspect(const T& a, const T& b, int)
    -> decltype(static_cast<bool>(a < b), void()) {
    std::cout << (static_cast<bool>(a < b)
                  ? "a is less" : "not less")
              << '\n';
}

// Запасная перегрузка.
template<class T>
void inspect(const T&, const T&, long) {
    std::cout << "not comparable\n";
}

int main() {
    inspect(3, 7, 0);
    inspect(Note{}, Note{}, 0);
}
```

Результат: `a is less`, затем `not comparable`.

Этот пример намеренно имеет третий служебный аргумент. Он не является данными сравнения; он нужен для явного приоритета перегрузок. Сейчас разберём отдельно и возвращаемый тип, и приоритет.

### 8.2. Почему возвращаемый тип после стрелки

Обычная функция `void f(int x)` объявляет результат перед именем. Можно эквивалентно написать `auto f(int x) -> void`. Такой синтаксис называется trailing return type.

Почему он нужен здесь? Потому что выражение `a < b` использует имена параметров. После списка параметров эти имена уже находятся в области видимости. Запись `auto ... -> decltype(...)` означает, что возвращаемый тип задан явно через выражение `decltype`, а не выводится из тела функции.

Разберём `decltype(static_cast<bool>(a < b), void())`:

- Сначала должно быть корректно выражение `a < b`.
- Затем должно быть корректно преобразование его результата к `bool`.
- Запятая связывает эту проверку с выражением `void()`.
- Тип всего выражения со встроенной запятой — тип правой части, здесь `void`.

Почему `void()`? Нам нужна функция, которая ничего не возвращает. Если написать только `decltype(a < b)`, тип результата для `int` будет `bool`, а наша функция ничего не возвращает. Приём с запятой проверяет левое выражение, но выбирает нужный тип результата. Ничего не вычисляется: всё внутри `decltype`.

В теле используем то же `static_cast<bool>(a < b)`, чтобы проверяемая операция и реальная операция точно совпадали.

### 8.3. Что происходит для int

При `inspect(3, 7, 0)` компилятор рассматривает обе декларации. Из первых двух аргументов выводит `T = int`.

В основной функции подстановка даёт `const int& a, const int& b`. Выражение `a < b` корректно, `static_cast<bool>` корректно, тип результата после запятой — `void`. Получилась допустимая функция.

Запасная функция тоже допустима: её объявление не требует сравнения.

Почему не неоднозначность? Третий аргумент `0` имеет тип `int`. У основной функции параметр `int`, поэтому совпадение точное. У запасной параметр `long`, требуется стандартное преобразование. Основная перегрузка предпочтительна.

### 8.4. Что происходит для Note

При `inspect(Note{}, Note{}, 0)` выводится `T = Note`. Подставляем этот тип в объявление основной функции. `a < b` некорректно, поэтому нельзя сформировать её возвращаемый тип. Компилятор исключает эту специализацию из кандидатов.

Это и есть SFINAE: Substitution Failure Is Not An Error, то есть неудача подстановки не является ошибкой сама по себе. В данном случае речь о некорректном выражении в непосредственном контексте объявления шаблона, поэтому часто говорят expression SFINAE.

Запасная функция не требует `<`, её объявление корректно. Она остаётся единственным подходящим кандидатом. Преобразование `int` в `long` допустимо, поэтому выбирается она.

Если удалить запасную перегрузку, вызов с `Note` всё-таки станет ошибкой компиляции: нет подходящей функции. SFINAE не означает, что все ошибки игнорируются. Оно означает, что конкретная неудачная подстановка не обязана разрушать весь процесс выбора.

### 8.5. Где SFINAE не срабатывает

Сравните с таким изменением:

```cpp
// Фрагмент: замена основной перегрузки.
template<class T>
void inspect(const T& a, const T& b, int) {
    // Ошибка окажется в теле, слишком поздно.
    std::cout << (a < b);
}
```

Теперь объявление подходит для любого `T`. При `Note` эта функция будет предпочтительнее запасной из-за `int`. Компилятор выберет её и обнаружит ошибку в теле. Запасная функция не спасёт.

Именно поэтому проверка размещается в объявлении: это не просто странный стиль записи. SFINAE ограничено непосредственным контекстом подстановки; ошибки, возникающие, например, как побочный эффект инстанцирования другой сущности, могут быть обычными жёсткими ошибками компиляции.

`auto` с выводом типа из тела — не замена `-> decltype(...)`: проверка, происходящая при выводе результата из тела, не является тем же непосредственным контекстом. Для первой демонстрации оставляем явный trailing return type.

**Плюсы:** можно быстро сделать условную перегрузку; подход работает до C++20. **Минусы:** возвращаемый тип превращается в сложную проверку, правила выбора приоритетов приходится выражать дополнительными средствами. При нескольких повторяющихся требованиях удобнее вынести проверку в отдельный признак типа.

## 9. void_t и enable_if: разделяем проверку и запрет

### 9.1. Сначала обычный признак типа

В предыдущей главе проверка прямо встроена в объявление одной функции. Но возможность сравнения полезна в нескольких местах: при выборе максимума, при сортировке, при формировании отчёта. Хотим отдельно получить ответ `true` или `false` для типа.

Начнём с того, как вообще представить логическое свойство типа в виде шаблона.

Запускаемый пример: [`17_type_trait.cpp`](examples/17_type_trait.cpp).

```bash
cmake --build build --target run-theory-17_type_trait
```

```cpp
#include <type_traits>

template<class T>
struct is_int : std::false_type {};

template<>
struct is_int<int> : std::true_type {};

int main() {
    static_assert(is_int<int>::value);
    static_assert(!is_int<double>::value);
}
```

`std::false_type` и `std::true_type` — стандартные типы с константным статическим членом `value`, равным соответственно `false` и `true`. Они являются специализациями `std::integral_constant<bool, ...>`.

`struct is_int : std::false_type {}` — обычное наследование. Собственный член `value` не определяем: наследуем его. Можно было написать `static constexpr bool value = false;` вручную; стандартные типы удобны тем, что соответствуют общепринятому интерфейсу traits.

`template<> struct is_int<int>` — полная специализация: для конкретного `int` используем другое определение. Поэтому `is_int<int>::value` истинно, для `double` выбирается основной шаблон и значение ложно.

Это учебная модель; в настоящем коде для сравнения типов достаточно `std::is_same_v<T, int>`. Нас интересует механизм специализаций.

### 9.2. Частичная специализация — выбор семейства типов

Полная специализация подходит для одного конкретного типа. Частичная может описывать целое семейство, например любые указатели:

Запускаемый пример: [`18_partial_specialization.cpp`](examples/18_partial_specialization.cpp).

```bash
cmake --build build --target run-theory-18_partial_specialization
```

```cpp
#include <type_traits>

template<class T>
struct is_pointer_like : std::false_type {};

template<class U>
struct is_pointer_like<U*> : std::true_type {};

int main() {
    static_assert(is_pointer_like<int*>::value);
    static_assert(is_pointer_like<double*>::value);
    static_assert(!is_pointer_like<int>::value);
}
```

Второй шаблон всё ещё имеет параметр `U`, но подходит не любому аргументу: только форме `U*`. Для `int*` компилятор сопоставляет форму и выводит `U = int`. Для `int` сопоставление не получается, остаётся основной шаблон.

Почему это важно? Мы хотим похожее поведение для любого типа, у которого допустимо сравнение. Но такой набор типов нельзя описать формой вроде `U*`: сравнимыми могут быть числа, строки и произвольные пользовательские классы.

Нужен способ сделать специальную форму шаблона доступной только тогда, когда некоторое выражение корректно.

### 9.3. Зачем дополнительный параметр, равный void

Введём служебный параметр, пока без всяких проверок:

```cpp
template<class T, class = void>
struct has_less : std::false_type {};
```

Первый параметр — проверяемый тип. Второй — просто тип, который будет участвовать в сопоставлении специализации. У него даже нет имени, потому что в основном шаблоне он не используется. Значение по умолчанию — `void`.

`has_less<int>` теперь означает `has_less<int, void>`. Почему `void`? Он удобен как нейтральный тип-маркер. Мы не создаём переменную типа `void` и не выделяем память. Здесь `void` — аргумент шаблона типа, что разрешено.

Пока любой тип даёт false. Хотим написать частичную специализацию, которая тоже соответствует `has_less<T, void>`, но только при допустимом `<`.

### 9.4. Откуда берётся void_t

Рассмотрим отдельно простейший alias template:

Запускаемый пример: [`19_void_t.cpp`](examples/19_void_t.cpp).

```bash
cmake --build build --target run-theory-19_void_t
```

```cpp
#include <type_traits>

template<class... Ts>
using my_void_t = void;

int main() {
    static_assert(std::is_same_v<
        my_void_t<int, double>, void>);
    static_assert(std::is_same_v<
        my_void_t<>, void>);
}
```

Он принимает любое число корректных типов и превращает их в `void`. Стандартный `std::void_t` из `<type_traits>` делает именно это.

Зачем такая функция от типов, если ответ всегда один? Потому что прежде, чем сформировать специализацию псевдонима, компилятор должен подставить и проверить его аргументы. `std::void_t<decltype(a < b)>` нельзя получить, если `decltype(a < b)` недопустимо. Никакого значения false при этом нет; просто подстановка не удаётся.

Различайте два случая:

`std::void_t<int>` корректно и равно `void`.

`std::void_t<decltype(некорректное_выражение)>` не равно false и не равно void: сформировать такой тип не получилось. Если это происходит при подстановке в подходящем SFINAE-контексте, кандидат или специализация отбрасываются. При прямом использовании некорректного псевдонима вне такого контекста будет ошибка.

### 9.5. Собираем has_less полностью

Теперь все составляющие уже известны. Соединим их.

Запускаемый пример: [`20_has_less.cpp`](examples/20_has_less.cpp).

```bash
cmake --build build --target run-theory-20_has_less
```

```cpp
#include <type_traits>
#include <utility>

// По умолчанию сравнение недоступно.
template<class T, class = void>
struct has_less : std::false_type {};

// Специализация доступна, только если
// можно сформировать второй аргумент.
template<class T>
struct has_less<T, std::void_t<
    decltype(static_cast<bool>(
        std::declval<const T&>() <
        std::declval<const T&>()
    ))
>> : std::true_type {};

struct Note {};

int main() {
    static_assert(has_less<int>::value);
    static_assert(!has_less<Note>::value);
}
```

Порядок чтения специализации — изнутри наружу:

1. `std::declval<const T&>()` моделирует два константных lvalue.
2. `<` проверяет наличие сравнения.
3. `static_cast<bool>` проверяет преобразование результата.
4. `decltype` превращает корректное выражение в тип `bool`.
5. `std::void_t<bool>` даёт `void`.
6. В итоге специализация имеет форму `has_less<T, void>` и наследует `std::true_type`.

Почему нельзя заменить всё выражение на обычное `void`? Тогда специализация `has_less<T, void>` подошла бы для любого `T`, и проверка исчезла бы. Именно попытка сформировать аргумент `void_t` создаёт условие.

### 9.6. Два сценария работы компилятора

Для `has_less<int>`:

- Запрошенный тип — `has_less<int, void>`.
- Проверяется частичная специализация; `T = int`.
- Выражение сравнения корректно, `decltype` даёт `bool`, `void_t` даёт `void`.
- Специализация соответствует запросу и более специализирована, чем основной шаблон.
- Результат — `std::true_type` через наследование, `value == true`.

Для `has_less<Note>`:

- Запрошенный тип — `has_less<Note, void>`.
- Проверяется та же частичная специализация; `T = Note`.
- Сравнение не существует, поэтому нельзя сформировать `decltype` и второй аргумент.
- Частичная специализация не подходит из-за неудачной подстановки.
- Используется основной шаблон, `value == false`.

Почему ошибка не приводит к остановке компиляции? Потому что компилятор пытается сопоставить частичную специализацию шаблона с запрошенным типом; некорректная подстановка в данном контексте делает эту специализацию неподходящей. Это применение SFINAE к частичной специализации, а не обработка исключения во время работы программы.

Такой стиль называют detection idiom: выражаем наличие операции как compile-time признак. Это удобно, если один и тот же признак нужен в разных местах. Недостаток — несколько уровней шаблонов, которые по отдельности ничего не говорят о прикладной задаче.

### 9.7. Печатаемость — ещё один признак

Для рейтинга нужно не только сравнение. Проверим потоковый вывод. Принцип тот же, но добавляется проверка конкретного возвращаемого типа.

```cpp
// Требуются <ostream>, <type_traits>, <utility>.
template<class T, class = void>
struct is_printable : std::false_type {};

template<class T>
struct is_printable<T, std::void_t<
    decltype(std::declval<std::ostream&>()
             << std::declval<const T&>())
>> : std::is_same<
    decltype(std::declval<std::ostream&>()
             << std::declval<const T&>()),
    std::ostream&
> {};
```

Внутри `void_t` проверяем, существует ли оператор вывода. Но наличие оператора ещё не гарантирует, что его результат — ссылка на поток. Поэтому вместо `std::true_type` наследуем `std::is_same<фактический_тип, std::ostream&>`.

`std::is_same` тоже предоставляет `value`. Если выражение существует, но результат не `std::ostream&`, специализация подходит, однако `value` равно false. Так мы проверяем две независимые вещи: допустимость операции и её результат.

В реальном коде можно вынести повторяющийся `decltype` в alias template, например `output_result<T>` из главы 7. Здесь оставили обе записи развёрнутыми, чтобы видеть, что они проверяют одно выражение.

Теперь объединим признаки:

```cpp
template<class T>
inline constexpr bool can_write_max_v =
    has_less<T>::value && is_printable<T>::value;
```

Это variable template: для каждого `T` получается константная переменная типа `bool`. `constexpr` требует вычислимого при компиляции значения. `inline` в C++17 удобно для определения переменной-шаблона в заголовке. Суффикс `_v` — соглашение об именовании значения признака, а не ключевое слово.

Сейчас у нас есть ответ, но пока нет запрета. `can_write_max_v<Note>` равно false, однако обычный `write_max` всё ещё можно попытаться вызвать. Как сделать так, чтобы этот ответ управлял допустимостью объявления функции?

### 9.8. enable_if: превращаем bool в наличие типа

У `std::enable_if` простая идея. Рассмотрим её отдельно, без сравнения и вывода.

Запускаемый пример: [`21_enable_if.cpp`](examples/21_enable_if.cpp).

```bash
cmake --build build --target run-theory-21_enable_if
```

```cpp
#include <type_traits>

template<bool B, class T = void>
struct my_enable_if {};

template<class T>
struct my_enable_if<true, T> {
    using type = T;
};

int main() {
    using A = my_enable_if<true, int>::type;
    static_assert(std::is_same_v<A, int>);

    // Ошибка, если раскомментировать:
    // using B = my_enable_if<false, int>::type;
}
```

Первый параметр `B` — не тип, а значение `bool`, известное при компиляции. Второй — тип, который хотим получить при истинном условии; по умолчанию `void`.

Основной шаблон пуст. Частичная специализация для `true` содержит вложенный псевдоним `type`. Поэтому при `true` можно обратиться к `::type`, а при `false` нельзя. Сам объект `my_enable_if<false, int>` как тип допустим; отсутствует только его член `type`.

Стандартная запись `std::enable_if_t<B, T>` — сокращение для `typename std::enable_if<B, T>::type`. Почему нужен `typename` в длинной форме? В зависимом имени компилятору нужно сообщить, что `type` — именно тип. Псевдоним `_t` позволяет не писать эту техническую деталь каждый раз.

Почему это полезно? Мы умеем получить логический признак, а SFINAE умеет исключать кандидата при невозможности сформировать тип. `enable_if` соединяет эти два механизма.

### 9.9. Первое ограничение функции — возвращаемый тип

Самая понятная начальная форма для нашей функции:

```cpp
template<class T>
std::enable_if_t<can_write_max_v<T>, void>
write_max(std::ostream& out,
          const T& a, const T& b) {
    out << (static_cast<bool>(a < b) ? b : a)
        << '\n';
}
```

Читаем возвращаемый тип: если `can_write_max_v<T>` истинно, функция возвращает `void`. Иначе сформировать возвращаемый тип нельзя, и по SFINAE кандидат исключается.

Это тот же механизм, что в expression SFINAE главы 8, но проверка операции теперь вынесена в именованные traits. Не нужно одновременно читать сравнение, печать, `decltype` и объявление функции.

Для `Score`, поддерживающего обе операции, `enable_if_t<true, void>` превращается в `void`. Для `Note` получается попытка сформировать `enable_if_t<false, void>`, которая исключает кандидат. Если другой перегрузки нет, компилятор сообщит о невозможности вызова.

### 9.10. Почему часто встречается enable_if_t<..., int> = 0

Следующая форма кажется сложнее, но делает то же самое. Сначала рассмотрим обычный шаблон с дополнительным параметром-значением:

```cpp
template<class T, int N = 0>
void demo(const T&) {}
```

`N` — целочисленный параметр шаблона, не параметр функции. Его можно указать как `demo<int, 5>(10)`, но по умолчанию он равен 0. Он известен на этапе компиляции.

Заменим тип `int` на тип, существующий только при истинном условии, и уберём ненужное имя `N`:

```cpp
template<class T,
         std::enable_if_t<can_write_max_v<T>, int>
             = 0>
void write_max(std::ostream& out,
               const T& a, const T& b) {
    out << (static_cast<bool>(a < b) ? b : a)
        << '\n';
}
```

При истинном условии это фактически `template<class T, int = 0>`. При ложном тип второго параметра не удаётся сформировать. Почему `int`? Нужен допустимый тип для параметра-значения, которому можно дать простое значение по умолчанию. `0` — произвольное служебное значение, не вычисляемый признак и не код ошибки.

Почему не `void`? Нельзя объявить параметр-значение типа `void`. В предыдущей форме `void` подходил как возвращаемый тип функции, здесь требуется тип значения.

Чем эта форма удобнее предыдущей? Возвращаемый тип остаётся читаемым (`void`), и подход можно использовать там, где возвращаемого типа нет, например у конструктора. Однако для первой встречи с `enable_if` форма через возвращаемый тип проще.

Не путайте с `template<class T, class = std::enable_if_t<...>>`: у последней формы ограничение находится в значении по умолчанию параметра-типа, которое в некоторых интерфейсах можно обойти, явно указав второй тип. Кроме того, две перегрузки, отличающиеся только такими значениями по умолчанию, могут оказаться повторными объявлениями. Не стоит копировать сложные шаблонные сигнатуры без понимания их устройства.

### 9.11. Полная программа C++17: проверяем весь путь

Ниже не новая теория, а сборка уже изученных деталей. Если какая-то строка кажется непонятной, вернитесь к соответствующему шагу выше.

Запускаемый пример: [`22_sfinae_write_max.cpp`](examples/22_sfinae_write_max.cpp).

```bash
cmake --build build --target run-theory-22_sfinae_write_max
```

```cpp
#include <iostream>
#include <type_traits>
#include <utility>

// Типы результатов проверяемых выражений.
template<class T>
using compare_result = decltype(
    static_cast<bool>(
        std::declval<const T&>() <
        std::declval<const T&>()));

template<class T>
using output_result = decltype(
    std::declval<std::ostream&>() <<
    std::declval<const T&>());

// Проверяем возможность сравнения.
template<class T, class = void>
struct has_less : std::false_type {};

template<class T>
struct has_less<T, std::void_t<compare_result<T>>>
    : std::true_type {};

// Проверяем возможность вывода и его результат.
template<class T, class = void>
struct is_printable : std::false_type {};

template<class T>
struct is_printable<T, std::void_t<output_result<T>>>
    : std::is_same<output_result<T>,
                   std::ostream&> {};

// Для максимума нужны обе операции.
template<class T>
inline constexpr bool can_write_max_v =
    has_less<T>::value && is_printable<T>::value;

// Если условие ложно, нет возвращаемого типа.
template<class T>
std::enable_if_t<can_write_max_v<T>, void>
write_max(std::ostream& out,
          const T& a, const T& b) {
    out << (static_cast<bool>(a < b) ? b : a)
        << '\n';
}

struct Note {};

int main() {
    static_assert(can_write_max_v<int>);
    static_assert(!can_write_max_v<Note>);
    write_max(std::cout, 3, 7);

    // Нет подходящей перегрузки:
    // write_max(std::cout, Note{}, Note{});
}
```

Вывод 7. Раскомментируйте последний вызов, соберите снова: теперь ошибка касается недоступности перегрузки. Сравните с неограниченным шаблоном главы 6. В обоих случаях некорректный вызов не компилируется, но по разным причинам.

**Что получили:** переиспользуемые compile-time признаки и условную доступность функции. **Что не получили:** короткую декларацию требований и простую диагностику. Нужно знать `decltype`, `declval`, специализации, `void_t`, `enable_if`, чтобы прочитать один интерфейс. Именно это станет причиной перехода к concepts.

## 10. Concepts: те же требования, но прямо на языке C++20

### 10.1. Почему не начинали с concepts

Если сегодня пишем новый код на C++20, чаще всего сразу выберем concepts. Но важно понимать задачу: мы проверяем операции и определяем доступность функции. Иначе `requires` будет ещё одним непонятным синтаксисом.

Начнём с одного простого требования, без объединения признаков.

```cpp
template<class T>
concept Comparable = requires(const T& a,
                              const T& b) {
    static_cast<bool>(a < b);
};
```

`template<class T>` говорит, что требование зависит от типа. `concept Comparable = ...;` объявляет именованное compile-time ограничение. Для конкретного типа оно имеет истинность: `Comparable<int>` истинно, `Comparable<Note>` ложно. Это не функция и не объект.

`requires(const T& a, const T& b) { ... }` — requires-expression. Оно проверяет требования к выражениям и даёт логический результат. Параметры `a` и `b` не являются реальными объектами, которые нужно создать. Это условные параметры для записи проверяемых выражений, аналогично тому, как мы моделировали аргументы через `declval`.

Строка `static_cast<bool>(a < b);` — простое требование (simple requirement). Оно проверяет, что выражение можно сформировать, но не выполняет его и не проверяет, истинно ли само сравнение. Точка с запятой после выражения обязательна в списке требований.

Вся запись заканчивается `;`, потому что это объявление concept.

Сравните с SFINAE: больше не нужны основной шаблон, частичная специализация и `void_t`. Компилятор напрямую проверяет выражение в предусмотренном для этого контексте.

### 10.2. Проверка типа результата

Для вывода нам мало существования операции. Нужен тип результата `std::ostream&`.

```cpp
#include <concepts>
#include <ostream>

template<class T>
concept Printable = requires(std::ostream& out,
                             const T& value) {
    { out << value }
        -> std::same_as<std::ostream&>;
};
```

`<concepts>` — заголовок стандартных concepts. `std::same_as<A, B>` требует совпадения типов A и B. `<ostream>` объявляет потоковый интерфейс.

Внутренние фигурные скобки `{ out << value }` — часть синтаксиса составного требования (compound requirement). После стрелки указывается ограничение на тип выражения. Здесь проверяется `decltype((out << value))`, то есть тип результата с учётом категории выражения, относительно `std::same_as<std::ostream&>`.

Почему у `same_as` явно указан только один параметр? В compound requirement компилятор подставляет тип выражения первым параметром. Поэтому смысл проверки — `std::same_as<decltype((out << value)), std::ostream&>`.

Можно записать простое требование `out << value;`, но тогда любой допустимый возвращаемый тип будет принят. Для нашего контракта с цепочкой вывода нужен составной вариант.

Дополнительное слово `noexcept` между `}` и `->` позволило бы потребовать отсутствие исключений у операции. Здесь оно не нужно: обычный потоковый вывод может бросать исключения.

### 10.3. Как ограничить функцию

```cpp
template<class T>
concept CanWriteMax = Comparable<T> && Printable<T>;
```

Объединяем два именованных требования через логическое «и». Это отдельное понятие: тип подходит для нашей конкретной функции.

Есть три равноправные формы объявления (это альтернативы, не три перегрузки, которые следует вставить одновременно).

```cpp
// 1. Requires-clause после template.
template<class T>
requires CanWriteMax<T>
void write_max(std::ostream&, const T&, const T&);
```

`requires CanWriteMax<T>` — requires-clause, условие доступности объявления. Это не requires-expression: после `requires` идёт уже готовое условие, а не блок проверки выражений.

```cpp
// 2. Requires-clause после параметров.
template<class T>
void write_max(std::ostream&, const T&, const T&)
    requires CanWriteMax<T>;
```

Удобно для функций-членов или когда ограничение хочется расположить рядом с сигнатурой.

```cpp
// 3. Ограниченный параметр шаблона.
template<CanWriteMax T>
void write_max(std::ostream&, const T&, const T&);
```

Здесь `CanWriteMax` вместо `class` обозначает ограничение на `T`. Семантика требования та же. Мы не передаём объект concept: `T` по-прежнему параметр-типа.

Для первой попытки лучше форма 1: она явно отделяет вывод типа от проверки требования. Когда запись привычна, форма 3 очень компактна.

### 10.4. Полная программа C++20

Запускаемый пример: [`23_concepts_write_max.cpp`](examples/23_concepts_write_max.cpp).

```bash
cmake --build build --target run-theory-23_concepts_write_max
```

```cpp
#include <concepts>
#include <iostream>

template<class T>
concept Comparable = requires(const T& a,
                              const T& b) {
    static_cast<bool>(a < b);
};

template<class T>
concept Printable = requires(std::ostream& out,
                             const T& value) {
    { out << value }
        -> std::same_as<std::ostream&>;
};

template<class T>
concept CanWriteMax = Comparable<T> && Printable<T>;

// Требование читается прямо из объявления.
template<CanWriteMax T>
void write_max(std::ostream& out,
               const T& a, const T& b) {
    out << (static_cast<bool>(a < b) ? b : a)
        << '\n';
}

struct Note {};

int main() {
    static_assert(CanWriteMax<int>);
    static_assert(!CanWriteMax<Note>);
    write_max(std::cout, 3, 7);

    // Ограничение не выполнено:
    // write_max(std::cout, Note{}, Note{});
}
```

Алгоритм `write_max` не изменился относительно C++17. Заменили только способ выразить требования. Для `int` выводится 7. Для `Note` ограничение ложно, функция не подходит. При раскомментированном вызове диагностика обычно указывает на невыполненное требование `Comparable` или `Printable`, хотя конкретный текст зависит от компилятора.

### 10.5. Concepts умеют больше, чем сокращать запись

Возьмём две перегрузки для отчёта: печатаемый объект можно показать, а если он ещё и сравнимый, доступны дополнительные действия.

Запускаемый пример: [`24_concept_overloads.cpp`](examples/24_concept_overloads.cpp).

```bash
cmake --build build --target run-theory-24_concept_overloads
```

```cpp
#include <concepts>
#include <iostream>

template<class T>
concept Printable = requires(std::ostream& out,
                             const T& x) {
    { out << x } -> std::same_as<std::ostream&>;
};

template<class T>
concept Comparable = requires(const T& a,
                              const T& b) {
    static_cast<bool>(a < b);
};

template<class T>
concept Rankable = Printable<T> && Comparable<T>;

template<Printable T>
void inspect(const T&) {
    std::cout << "print only\n";
}

template<Rankable T>
void inspect(const T&) {
    std::cout << "print and compare\n";
}

struct Label {};

std::ostream& operator<<(std::ostream& out,
                         const Label&) {
    return out << "label";
}

int main() {
    inspect(Label{});
    inspect(7);
}
```

Вывод `print only`, затем `print and compare`.

Для `Label` выполняется только `Printable`. Для `int` обе перегрузки допустимы. Почему выбирается вторая? Ограничения учитываются при разрешении перегрузок. `Rankable` включает то же именованное требование `Printable<T>` и дополнительно `Comparable<T>`, поэтому оно более ограничено по правилам subsumption.

Это не значит, что компилятор решает произвольные логические задачи. Если заново выписать внешне эквивалентное выражение вместо использования того же concept, атомарные ограничения могут оказаться разными и выбор — неоднозначным. Поэтому переиспользуем именованные concepts, когда хотим явно выстроить отношения между требованиями.

В классическом SFINAE наличие двух `enable_if` с истинными условиями само по себе не задаёт приоритет. Часто приходится добавлять служебные параметры или делать условия взаимоисключающими. Concepts позволяют выразить этот приоритет ближе к смыслу интерфейса.

### 10.6. Чего concepts не гарантируют

Наш `Comparable` проверяет конкретную операцию `<` и преобразование результата. Он не проверяет, что оператор действительно задаёт правильный порядок. Например, оператор может всегда возвращать true. Тогда тип удовлетворит синтаксической проверке, но нарушит требования сортировки.

`std::totally_ordered` из `<concepts>` требует гораздо больше операций, в том числе равенство и отношения `<=`, `>`, `>=`, а также подразумевает семантические требования. Для `write_max` нам не нужны все эти операции, поэтому собственный минимальный concept обоснован. И даже стандартный concept не способен автоматически доказать соблюдение всех математических свойств для пользовательского типа.

Concepts не превращают любую ошибку в теле функции в ложное требование. Если забыли проверить операцию, а затем применили её в реализации, ошибка всё ещё возможна. Контракт должен отражать реально используемые операции.

Преимущества: понятные именованные требования, обычно лучшая диагностика, явное участие ограничений в выборе перегрузок. Недостатки: нужен C++20; надо разобраться в правилах constraints, а слишком строгие или слишком слабые требования делают интерфейс хуже. Для старых библиотек C++17 и некоторых низкоуровневых задач метапрограммирования SFINAE и traits остаются актуальны.

## 11. Как связать всё в голове перед семинаром

Теперь можно восстановить весь путь без заучивания синтаксиса.

В начале мы передавали алгоритму правило сравнения. Обычной функции достаточно, если состояние не нужно. Функтор нужен, когда состояние и вызываемое поведение должны принадлежать одному объекту. `bind` адаптирует уже существующую функцию, лямбда позволяет выразить адаптацию прямо и локально.

Затем создали обёртку. Обычная передача по значению теряет информацию о категории аргумента, const-ссылка делает его константным lvalue. Вывод `T&&` сохраняет тип и категорию через специальное правило вывода и reference collapsing; `std::forward<T>` использует эту информацию при дальнейшей передаче.

Когда стало нужно разное число аргументов, variadic templates позволили формировать сигнатуры на этапе компиляции, а fold expressions — обрабатывать пакет без ручной рекурсии. Для чтения достаточно const-ссылок; для передачи конструктору используем forwarding каждого аргумента.

Наконец, обобщили функцию на произвольный тип и поняли, что далеко не все типы подходят. `decltype` определяет тип выражения, `declval` моделирует аргумент нужной категории без создания объекта. Expression SFINAE позволяет исключить кандидат при неудачной подстановке в объявление. `void_t` делает удобно переиспользуемый признак, `enable_if` превращает логическое условие в наличие или отсутствие типа. Concepts выражают эти требования непосредственно и позволяют упорядочивать связанные ограничения.

### Проверка собственного понимания

Попробуйте объяснить вслух следующие ситуации, не глядя на код.

**Почему `std::move` внутри relay неправилен?** Потому что превращает и исходные lvalue в rvalue, разрешая забрать ресурс, хотя вызывающий этого не выражал. `forward` учитывает выведенный `T`.

**Почему не нужно `forward` в каждой функции с шаблоном?** Если мы только читаем объект, const-ссылка проще и отражает контракт. Perfect forwarding нужен именно для прозрачной передачи аргумента дальше.

**Почему пакет не обычный vector?** Пакет определяет отдельные параметры и их типы при компиляции. Vector хранит элементы одного типа, число которых может меняться во время работы.

**Почему `void_t` не всегда даёт void?** Для корректных аргументов даёт всегда. Но если тип аргумента невозможно сформировать, до корректной специализации псевдонима дело не доходит.

**Почему `enable_if` не просто bool?** Булево значение false само по себе не делает объявление функции некорректным. Отсутствие требуемого вложенного типа при подстановке делает.

**Почему ошибка в теле не SFINAE?** Функция уже выбрана; компилятор не пробует запасную перегрузку из-за неудачи в теле.

**Почему при concepts всё ещё нужен контракт алгоритма?** Проверка выражений не доказывает семантику. Например, правильность строгого слабого порядка остаётся ответственностью автора компаратора.

### Что обязательно показать студентам

Для первого занятия достаточно одного сравнения через обычную функцию, функтор, bind и лямбду; одного примера копирования/перемещения с обёрткой; одного примера печати пакета с рекурсией и fold. Не начинайте занятие с таблицы всех категорий выражений или четырёх форм fold: сначала проблема, затем ровно та теория, которая её решает.

Для второго занятия начните с обычного `write_max`, попробуйте тип без операторов, затем покажите запасную перегрузку из главы 8. После этого имеет смысл разобрать `void_t` и `enable_if` по отдельности. Завершите переносом того же алгоритма на concepts. Основной критерий успеха — студент может объяснить, какую именно ошибку предотвращает ограничение и почему проверка находится в объявлении.

Дополнительные детали (все формы fold, ограничения стандартных concepts, тонкости subsumption) изучайте сами для ответов на вопросы, а не как обязательный объём лекции.
